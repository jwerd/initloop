# Restricted and proportional onboarding

## Establish what is available

Use supplied capability/policy evidence and existing project conventions before selecting mechanisms. Inspect a permitted project file or known runner, not a matrix of denied locations/tools. Record a helper as unavailable/denied when evidenced; do not retry equivalent invocations or read its denied source through another interpreter. A denied helper does not automatically prohibit distinct ordinary project tests; a broad execution prohibition does. Interpret the actual scope, not the outcome you want.

Prefer project-local ignored scratch/config and existing dependencies. When a read-only inventory excludes a symlink or inaccessible input, continue other permitted inputs and preserve exclusions/provenance. Do not follow an escaped/private target, materialize a link to evade snapshot restrictions, or claim complete coverage. Internal/dangling/cyclic links can be ordinary layout facts; they are not permission to read outside scope. Read-only metadata tolerance does not weaken copy/repair/execution security.

## Continue after a blocked step

Choose a genuinely allowed alternative for the objective: inspect existing Make/package scripts, use an established runner or run ordinary tests/smokes within allowed paths. Preserve baseline failures and observed results. Missing Docker/helper/subagent access is not proof that the application cannot run. Do not introduce a container, install tools, copy a prohibited helper, disable hooks, relax policies or rephrase a refused command to bypass controls.

A useful partial result can include verified setup/build, local data operations and tests while login or an external service remains blocked. Keep verification strength explicit: direct project commands are scoped observations, not unexecuted helper acceptance. When a requested full gate is unavailable, state it and continue independent work; do not silently call it complete. No requirement to spawn a fresh agent or freeze controller state for every small local setup request.

## One precise request when necessary

Separate evidence that would be nice to add from access required for the requested usable outcome. If permitted core checks already establish useful partial progress and a missing input still gates the flow, do not request extra permission merely to certify optional HTTP/transport or full-verification checks. Mark them unverified under the known restriction. If the user explicitly requires a running HTTP service or network behavior, that access may instead be indispensable: prepare the actual minimal request and combine related essential needs. The reason text of a command approval is not an enforcement boundary; never describe a whole-command escalation as a granular host/network grant.

Before asking, collect the observed failure, affected flow, source/config name, what already works and the smallest missing input/access/intent. Combine related requirements without bundling optional permissions. Ask for an existing supported project-local input when that is sufficient rather than broad filesystem/network access. Never collect or print secret values in the report. A denied access scope is evidence, not a challenge: reuse it and stop repeating the operation until scope changes. A prior approval applies only to its action/scope, not all future work.

Escalation disabled does not authorize bypass. Report a blocked operation and its minimal user action/input; do not promise automatic retry or approval. Questions about product intent or a missing input remain legitimate where indispensable. Record actual answers with their scope; simulated evaluation replies must remain labeled, never real user approvals.

## Per-flow outcomes

Use a concise table/list, based on executed commands and source locations:

| Flow | State | Evidence / reason | Smallest remaining action |
| --- | --- | --- | --- |
| Local setup and data action | verified only after execution | Command/result at tested working state | None, or precise untested edge |
| Authenticated operation | blocked if required input/access is absent | Observed missing configuration name or actual permission/network failure | Supply that evidenced input/access, without values in the report |
| External provider fidelity | unverified unless exercised | Mock/skip or unexecuted integration | Permitted actual integration check |

Do not invent key names from a generic auth error. HTTP200, a rendered login page, a passing mock or successful migration does not prove authenticated/business readiness. Distinguish blocked (observed impediment), unverified (not established) and verified (executed assertions with scope). If a network check was not allowed, say so without probing repeatedly. Include a running URL and exact owned stop only for a persistent service actually left running; otherwise say services stopped/never launched. Keep existing data and unrelated resources intact.
