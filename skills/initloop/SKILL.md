# Initloop

Own discovery, repair and independent verification. Use the invoking harness's reasoning and native agents; never extract harness credentials or introduce model API/auth clients. Exclude secrets before sharing source context. Use actual harness permissions and project policy; this skill adds no permissions and imposes no universal container requirement.

Run deterministic helpers with `python3 <this-skill>/scripts/initloop.py --help`. Static work needs Python 3.9+ and Git, not Docker. Read [controller.md](references/controller.md) for runtime and lifecycle commands, [harnesses.md](references/harnesses.md) for fresh-agent verification, and [local-services.md](references/local-services.md) for inaccessible dependencies.

1. **Discover before choosing a runner.** Inspect Git/user changes, existing instructions, docs, manifests AND lockfiles, setup/run scripts, config templates, CI and runner definitions. Run `audit PROJECT` and `workflow PROJECT`. Trace actual consumers for app server, every named database/engine/version, cache, queue/workers, API and storage relationships; inspect images, ports, volume paths and network needs. Record source locations, declared/resolved/runtime-observed versions separately, conflicts and unknowns. Static observations are not successful runtime evidence. An undocumented connection is not proof that its service is inaccessible.
2. **Preserve existing conventions.** Try the established setup first within authorized tools. Keep working native scripts, Compose/Sail/devcontainers or other project runners. Do not replace them just because another runner is familiar. If no usable local runner is established, offer suitable native/Compose/other supported options with concrete dependency, portability, persistence and isolation tradeoffs, then obtain only a meaningful unresolved choice. Decide routine reversible details independently. Docker is an option, not a prerequisite; native execution uses host permissions and is not sandboxed. Never silently downgrade a chosen isolated runtime or bypass actual harness restrictions. Do not repeatedly ask for skill exceptions to already-authorized execution.
3. **Establish the objective and baseline.** Freeze independently sourced assertions before repairs with `begin PROJECT --runs OUTSIDE_PROJECT --contract CONTRACT.json`, protecting evaluator/tests with `protected_paths`. Snapshot only tracked nonsecret inputs (`--include-dirty` explicitly includes tracked changes). Keep hidden expectations/controller state outside newcomer contexts. Give a genuinely fresh newcomer only the project/snapshot, skill and plain objective plus declared machine prerequisites. Log observed failures separately from inferences and missing information. If fresh context/tool isolation is unavailable, report assisted-context verification, not enforced blindness.
4. **Repair the useful workflow.** Map dependencies to configuration and consumers; prefer existing adapters and same-engine synthetic data where warranted. Label inferred schemas and API simulations provisional. Preserve production behavior/tests. `repair RUN --files CHANGES.json` generates an isolated reviewable patch; adoption into the real checkout requires task authorization. Normal development commands must work without Initloop. Disposable verification is separate from persistent services: use existing lifecycle commands first, or the optional native `dev` helper for owned foreground processes. Track resource identities, retained data, logs, exact stop command and reset scope. Preserve unrelated services/data. Keep the app running when requested/demo requires it; do not report disposable execution as a lasting environment.
5. **Publish project knowledge, not generic instructions.** Offer reconcile (recommended), preserve (report only), or replace explicitly selected files before adopting instructions. `workflow --destination OUTSIDE_PROJECT --mode MODE [--select FILE]` produces proposals, not source edits. Preserve existing team/scoped policies and recoverable originals; policy replacement is refused. Adopt concise AGENTS.md/CLAUDE.md links to `docs/initloop-stack.md`, `docs/initloop-runbook.md` and workflow guidance. Complete static drafts with actual commands, configuration names (no secrets), dependencies, versions/evidence, unknowns, selected runner rationale, synthetic fidelity, ownership/stop/reset, tests/debugging, tested revision and runtime results. Clearly label proposed, adopted and verified state. Existing shared docs are reconciled manually, never overwritten blindly. MCP declarations do not prove authenticated availability; do not install tools implicitly.
6. **Verify independently.** Two clean acceptance runs can use `verify RUN --runner native` for authorized host execution, or `--runner docker --image LOCAL_IMAGE` for the constrained disposable backend. Use a fresh agent with adopted project instructions for real setup and a small change/test cycle. Verify useful persisted outcomes, setup reruns in the same working directory/database (exact seed counts and preserved user records), restart/reopen/reset, errors/timeouts/auth where relevant, and logs. Verify complete runbook commands and map contract operations to probes or explicit exclusions. Use returned record IDs and before/after counts with extra records; verify the actual owned foreground/background stop modes and scoped reset/reseed, marking untested reset unverified. Assert egress restrictions only where actually configured/tested; native networking is not restricted by the helper. Preserve failed evidence; bounded repair attempts remain three. Other project runners can be exercised through authorized harness tools with equivalent evidence; don't label them helper-certified without actual helper execution.
7. **Maintain and deliver.** `refresh PROJECT --manifest PROVENANCE.json` detects changed inputs, never recertifies runtime. Revalidate affected commands/services, update accurate docs and preserve old evidence. Report exact tested revision/working state, prerequisites, runner decision, changes, useful behavior, unavailable checks and substitute fidelity. Include running URL/command and exact stop instructions for persistent demos. Distinguish onboarding, daily development, instruction loading and real-provider fidelity; do not announce unmet gates complete.

No publishing, billing, production data access, external resets, deployment or automatic patch application is implied. Never expose credentials/home/Docker sockets as a convenience. Actual host/project restrictions remain authoritative.
